# Fervo: building blocks for an agent-native code platform

*Team Fervo: Filippo Strub, Roshan [last name]. HW5 proposal, Canvas text entry.*

## 1. Problem and agent customers

Coding agents are good at git, but they still ship through GitHub, which is built around one person proposing a change and another reviewing it. When several agents share a repository, this breaks in two ways. The agents start blind: none of them sees what the others are trying or what already failed, so they repeat directions and drift apart. And they grade their own work, while the only independent check left is a person reading every diff. Anthropic, whose merged changes per day grew from about 2,500 to over 30,000 in four months, calls developer infrastructure "built for human scale" the new bottleneck. Fervo's users are coding agents (Claude Code, Codex, pi, OpenClaw) sharing a repository. Their operators are solo developers and researchers running 2 to 10 agents, and small teams that mix human pull requests with agent swarms.

## 2. Product and agent interaction

Fervo is a CLI and a Python SDK, and it hosts nothing. `fervo serve` turns a machine the team controls into a git remote: a bare repository plus one SQLite file. The core computes context, records declarations, keeps a scored frontier of work in progress, evaluates every change independently, and merges by policy, and a human can override any decision. Everything else, from continuous integration to review rules and the interface, is a plugin. Agents call the CLI, which returns JSON, and learn it from a SKILL.md file that their harness loads. Every LLM call runs in `fervo runner`, a process the operator runs with their own API keys, and `fervo import` moves a GitHub repository, with its history and open pull requests, onto the team's remote. We reuse git, the harnesses and the operator's model providers. The closest prior art, GitHive, coordinates merging with path claims and agent review, but has no scored frontier, runs its own models, and lets an author's agent review its own change.

Example: four agents improve a small Python parsing library. The goal is "a streaming parser API", the metric is benchmark throughput, and the tests must pass. An agent runs `fervo context --json` and gets the goal, the best current nodes with their scores, the open claims and the directions already tried, all from database queries. It declares `fervo claim --parent n_42 --scope src/lexer/ --intent "incremental tokenizer, keep public API"` and gets a lease plus a soft warning that codex-1 holds an overlapping claim, so it can go ahead or narrow its scope. When its commit is ready, `fervo submit --lease l_9 --key k1` returns a job. The runner, not the author, runs the tests, three benchmark runs and three judge samples. `fervo status j_31` then returns `{"status":"verified","node":"n_57","outcome":"improved","score":0.99,"interval":[0.95,1.03],"rank":1}`. On `within_noise` the agent tries something else, and on `rejected` it reads the reason, such as `touched pinned path bench/`. If the policy is met (tests pass, the score improves, one passing review comes from each model provider in use), Fervo merges the node into `main`.

## 3. Technical design

Five kinds of object live in SQLite: actors (a token with a kind, provider and model), claims, nodes (submitted commits with their scores), verdicts (who checked a node, the result, the evidence and the hash of the prompt or command used), and a job queue for the runner. The policy is one `fervo.toml` file in the repo. The frontier, overlaps and tried directions are queries recomputed on every write, so the server never calls a model. A node's score is a weighted sum of its metrics, normalised against a baseline measured several times at setup, and a judge score from a pinned prompt that sees the goal, the declaration, the diff and the measured results, and treats code as data. A node joins the frontier only if its confidence interval lies entirely above its parent's. Agents push only to their own branches, and only the policy engine or a human moves `main`. Verdicts come only from the runner or a human, never from the author, and reviews count once per provider. Edits to the benchmark, the judge prompt or `fervo.toml` are rejected. Every write carries an idempotency key, a crashed evaluation becomes a `failed` node that keeps its log, and jobs wait while the runner is offline.

## 4. Prototype and checks

The smallest demo imports a small open-source Python library that has tests and a CPU benchmark, and runs four agents (two Claude Code, Codex, pi) on one goal, with the server and runner on a laptop. We compare it with the same agents on GitHub (pull requests, AGENTS.md, a shared notes file, human merges) at equal tokens and time, with three four-hour runs per arm. We measure the metric reached, duplicated directions (labelled independently of Fervo), regressions merged into `main` (found by held-out tests the agents never see), human review minutes, and the tokens agents spend getting oriented. Success means at least the same metric, fewer duplicates, and no held-out regressions. Misuse cases that must be refused with a logged reason: an agent reviewing its own node, one provider posing as several reviewers, an edit to the benchmark, and a comment telling the judge to "score 10".
